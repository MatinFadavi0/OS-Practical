# پاسخ تمرین ۴ — لنگر: کنترل منابع پردازه

## محیط اجرا

- کرنل: <bdi>`Linux 7.2.11-arch1-1`</bdi>
- معماری: <bdi>`x86_64`</bdi>

## پرسش‌های گزارش

### ۱. چرا محدودیت را پیش از <bdi>`exec`</bdi> و در مسیر فرزند اعمال کرده‌اید؟ اگر آن را فقط در پدر تنظیم کنید چه تغییری ایجاد می‌شود؟

ماسک <bdi>CPU</bdi> را با <bdi>`sched_setaffinity(0, ...)`</bdi> و حد فضای آدرس را با <bdi>`setrlimit(RLIMIT_AS)`</bdi> تنظیم کردم. هر دوی این‌ها ویژگی **خود پردازه** هستند. بعد از <bdi>`exec`</bdi> سر جایشان می‌مانند و به فرزندهای بعدی هم ارث می‌رسند.

**چرا در فرزند؟** بعد از <bdi>`fork`</bdi> فرزند یک پردازهٔ جداست. پس هر چیزی که آن‌جا عوض کنم فقط روی خودش و برنامه‌ای که <bdi>`exec`</bdi> می‌کند اثر می‌گذارد و لنگر دست نمی‌خورد.

**چرا قبل از <bdi>`exec`</bdi>؟** وقتی <bdi>`exec`</bdi> موفق شود دیگر هیچ کدی از لنگر در فرزند نمانده که بخواهد چیزی را تنظیم کند. اگر هم پدر بعداً از بیرون تنظیمش می‌کرد ممکن بود برنامه یک مدت بدون محدودیت اجرا شده باشد.

**اگر فقط در پدر تنظیم کنم:**

- برنامه باز هم محدود می‌شد چون از پدر ارث می‌برد. ولی مشکل این است که **خود لنگر هم محدود می‌شد**. صورت سؤال این را منع کرده و آزمون <bdi>`combined_controls`</bdi> هم چک می‌کند که ماسک و حد لنگر عوض نشده باشد.
- پردازهٔ معمولی حد hard را فقط می‌تواند پایین بیاورد. اگر پدر حد خودش را کم کند بدون دسترسی ویژه دیگر نمی‌تواند آن را برگرداند.
- حد <bdi>`RLIMIT_AS`</bdi> روی حافظهٔ خود لنگر هم اعمال می‌شد و ممکن بود خود لنگر قبل از <bdi>`fork`</bdi> به سقف برسد.

خروجی واقعی: این‌جا لنگر در حال اجراست. فرزند محدود شده ولی خود لنگر دست‌نخورده مانده است (<bdi>`$!`</bdi> همان PID لنگر است):

<div dir="ltr" align="left">

```
$ ./q2/langar run --cpus 0 --as-limit-mib 64 -- sleep 3 &
$ grep Cpus_allowed_list /proc/$!/status                       # langar
Cpus_allowed_list:	0-19
$ grep 'Max address space' /proc/$!/limits                     # langar
Max address space         unlimited            unlimited            bytes
$ grep Cpus_allowed_list /proc/$(pgrep -P $!)/status           # child (sleep)
Cpus_allowed_list:	0
$ grep 'Max address space' /proc/$(pgrep -P $!)/limits         # child (sleep)
Max address space         67108864             67108864             bytes
```

</div>

### ۲. چرا ممکن است برنامه حتی پیش از تخصیص حافظهٔ مورد انتظار شما به علت بارگذاری کتابخانه‌ها و نگاشت‌های دیگر به <bdi>`RLIMIT_AS`</bdi> برسد؟

<bdi>`RLIMIT_AS`</bdi> اندازهٔ **کل فضای آدرس مجازی** پردازه را محدود می‌کند و فقط به حافظه‌ای که برنامه با <bdi>`malloc`</bdi> می‌گیرد مربوط نیست. حتی قبل از این‌که <bdi>`main`</bdi> اجرا شود این‌ها در فضای آدرس نگاشت شده‌اند:

- کد و دادهٔ خود فایل اجرایی
- بارگذار پویا (<bdi>`ld.so`</bdi>) و کتابخانه‌های اشتراکی مثل <bdi>`libc`</bdi>. این‌ها در <bdi>RAM</bdi> بین پردازه‌ها مشترک‌اند ولی در فضای آدرس هر پردازه جدا حساب می‌شوند.
- پشته و <bdi>heap</bdi> اولیه و <bdi>vDSO</bdi> و فایل‌هایی مثل <bdi>locale</bdi>
- رزروهای بزرگی که هنوز به حافظهٔ واقعی تبدیل نشده‌اند مثل <bdi>arena</bdi>های <bdi>malloc</bdi> و پشتهٔ <bdi>thread</bdi>ها

پس ممکن است <bdi>RSS</bdi> کم باشد ولی فضای آدرس از همان اول چند مگابایت است.

خروجی واقعی: <bdi>`/bin/true`</bdi> هیچ حافظه‌ای نمی‌گیرد ولی با سقف ۱ مگابایت حتی <bdi>`libc`</bdi> را هم نمی‌تواند بار کند. <bdi>`python3`</bdi> هم موقع شروع حدود ۱۷ مگابایت فضای آدرس دارد و با سقف ۱۶ مگابایت بالا نمی‌آید:

<div dir="ltr" align="left">

```
$ ./q2/langar run --as-limit-mib 1 -- /bin/true
/bin/true: error while loading shared libraries: libc.so.6: failed to map segment from shared object
$ python3 -c 'print(open("/proc/self/status").read().split("VmSize:")[1].split()[0])'
17572
$ ./q2/langar run --as-limit-mib 16 -- python3 -c pass
Fatal Python error: init_import_site: Failed to import the site module
$ ./q2/langar run --as-limit-mib 32 -- python3 -c pass      # exit 0
```

</div>

## محدودیت‌های شناخته‌شده

- <bdi>`--cpus`</bdi> فقط فهرستی از شماره‌ها را قبول می‌کند که با ویرگول جدا شده‌اند و بازه‌ای مثل <bdi>`0-3`</bdi> را پشتیبانی نمی‌کند.
- اگر سقف <bdi>`--as-limit-mib`</bdi> آن‌قدر کم باشد که بارگذاری برنامه شکست بخورد خطا را خود بارگذار پویا می‌دهد و لنگر همان کد خروجش (مثلاً ۱۲۷) را برمی‌گرداند. اگر خود <bdi>`execvp`</bdi> با <bdi>`ENOMEM`</bdi> شکست بخورد لنگر کد ۱۲۶ می‌دهد.
- محدودیت‌های تمرین ۳ هنوز سر جایشان هستند: <bdi>`/proc`</bdi> و فایل‌سیستم جدا نشده‌اند و سیگنال‌ها به <bdi>PID 1</bdi> ایزوله منتقل نمی‌شوند.
